# 执行前纠错清单

这个文件记录用户在搜索、事实抽取、测试报告和角色回复链路中反复纠正过的问题。继续处理本项目相关任务前，先读一遍本文件，避免重复犯错。

## 总原则（重要！！！）

- 不要用无意义枚举解决问题。尤其不要为了覆盖某个测试问题，列一堆只对这个问题针对性很强且很具体的触发词。纠错的时候也不允许穷举反例替换。优先修通用逻辑、结构解析、来源优先级、事实抽取规则。
- 不要在没有用户批准的情况下偏离已确认的主链路。路线变化前先说明原因和影响。
- 不要反复大改同一条链路。改动前先判断最可能有效的最小改法，并控制 API 调用次数。
- 发现测试明显不合格时，停止继续跑后面的题，先修当前题。
- 不要为了让答案显得“绝对正确”而矫枉过正。角色聊天可以自然评价和接话；只要不违反资料里的明确事实即可。

## 搜索链路

- 二次元角色原作/设定类问题优先查萌娘百科，Andy 对话除外。
- 优先使用直达词条和豆包搜索。旧的 Tavily/DuckDuckGo 兜底链路不要随手复活。
- 如果旧兜底链路残留在当前执行路径里，优先移除或隔离，而不是继续在旧链路上修补。
- 角色问题里用户常用姓、名、称呼或代称时，应先映射到角色全名，再用全名查词条。
- 联网计划应解析主要对象和次要对象，按主次对象分别搜索干净对象名。不要把整句问题、感想、关系词拼进搜索词。
- 一个问题可以同时搜多个相关词条；不要因为先搜到一个对象就忽略同等重要对象。
- 对喜好/习惯类角色问题，物品名、动物名等通常不是要直达的角色词条；优先查当前角色或被问角色词条。
- 站点优先级要在日志里写清楚。直达、豆包 Custom/Global、本地百度/维基解析等格式要统一。

## 网页内容和事实抽取

- 三次元现实制作信息必须过滤：导演、编剧、制作团队、企划、公司、声优、访谈、活动、演唱会、上映播出、现实发售、厂牌、特典、榜单、商业运营等。
- 但作品本体、官方角色资料或作品内补充栏目里体现的角色设定、喜恶、经历、关系、台词，即使带有出处说明，也应视为作品内事实，不要误判成三次元制作信息。
- facts 应由豆包/火山方舟事实抽取为主，不要回到程序自己费劲截句子、容易截错的旧模式。程序补充只能做结构化、通用的小兜底。
- 萌娘百科资料框必须保留字段边界。例如“喜好动物：金鱼。鎹鸦：艳。”不能清洗成“喜好动物 金鱼 鎹鸦 艳”，否则会把不同字段强行建立关系。
- 不要把网页里的相邻角色、相邻条目、查论编、目录、导航、编辑提示、繁体变体页面噪声混进摘要。
- 搜索结果如果命中了页面但 facts 不完整，要判断是正文没送全、抽取器误判、还是停止降级阈值过早；不要只看“直达成功”。
- “直达成功”必须同时说明返回内容情况：命中哪个页面、正文长度、抽取 facts 数、关键 facts 是否覆盖用户问题。
- 如果 facts 覆盖充分但最终回答逻辑错，优先考虑增加时间线/约束层，而不是继续改搜索。

## 时间线和回答

- 事件经过、人物关系、相互影响、救赎、关系变化类问题需要时间线层。
- 时间线要保证大体顺序正确，覆盖关键转折；不要求事无巨细列出每个节点。
- 最终回答不是百科复述。复杂事件可以漏掉非核心节点，只要大体完整、没有原则性事实错误。
- DeepSeek 擅长语言表达，但可能整合错主体、对象、时间顺序。给 DeepSeek 的事实要清楚标明动作主体、对象、时间线和必要约束。
- 不要让角色说自己不可能知道的三次元信息，比如歌曲被用作动画 OP/ED、现实发行、活动、榜单等。作品内角色若设定为作曲者，可以用第一人称谈创作。
- 如果资料只支持“听说/资料里提到”，角色回答也应保留这种不确定性，不要说成亲眼见过。

## 名字、翻译和称呼

- 人名翻译优先把人名单独识别出来，再走翻译/映射，不要让人名和上下文一起被模型误翻。
- 不要把不容易错、没有假名的名字重新塞回映射表制造冗余。
- 对日文名本身是假名的角色，需要基于日文到中文表生成中文到日文的反向识别能力，避免模型把“清、澄、奈穗”等生成错误汉字。
- 每个角色对其他角色的称呼应按角色分别配置；称呼规则应进 prompt，不要靠回答后替换或穷举反例硬修。
- 翻译时性别信息可以从 facts 中标注给翻译 prompt 使用，但不要把“（男）/（女）”读进角色台词。
- MyGO!!!!! 是专有名词，分句/TTS 时作为整体处理，不要把多个感叹号拆成多句。只针对 MyGO!!!!! 这种实际专名处理，不要无意义扩展。

## 测试和报告

- 跑测试集时，一题一题跑。当前题结果不合理就停下来修，不要继续跑后面的题。
- 合格题日志保留在同一个总报告里；不合格题重跑时覆盖该题段落，不要不断新建零散报告。
- 报告日志要清楚展示每层具体情况：执行了什么、命中几条、正文几条、抽取几条 facts、是否进入下一层。
- 日志格式要统一，例如：
  - `搜索步骤[P0 萌娘百科/主站点][直达]: ...`
  - `搜索结果[P0 萌娘百科/主站点][直达]: ...`
  - `层级判断[P0 萌娘百科/主站点]: ...`
- 报告里不要展示用户已知且冗长的本地【角色设定资料】块。
- 不要每次刷新掉前面已合格题的日志。单题重跑只替换对应题。
- 如果只是重新格式化报告，优先用已有 state 重新生成，不要调用远程 API。

## 额度控制

- 用户对 API 额度非常敏感。不要无计划地反复跑完整测试集。
- 修改前先判断问题发生在哪一层：搜索计划、直达取页、内容清洗、事实抽取、时间线整理、DeepSeek 回答、翻译、TTS 分句或报告展示。
- 能用本地检查、已有 state、已有报告验证的，不要调用远程 API。
- 需要远程验证时，只跑当前问题，不跑全套。
