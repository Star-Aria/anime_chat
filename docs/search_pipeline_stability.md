# 联网回答稳定化说明

## 先说结论

联网回答不是一次模型调用，而是一条流水线：

1. 搜索计划判断要查什么。
2. 直达网页或搜索 API 取得资料。
3. facts 模型从资料中抽取事实。
4. 时间线模型整理事件顺序。
5. DeepSeek 以角色口吻回答。
6. 翻译模型生成中文显示文本。

以前的测试主要查看第 6 步的最终结果。只要答案不对，就必须重新运行整条流水线，既无法准确定位问题，也会重复消耗 API 额度。

现在增加了三道稳定装置：运行记录、结构化门禁和固定回放基线。

## 一、运行记录解决“到底调用了多少次”

`WebContextService.buildContextDetailed()` 会返回：

- 最终联网资料 `context`
- 本轮运行记录 `trace`

`trace` 只记录安全的元信息，不保存 API Key：

- 豆包搜索 API 调用了几次
- 搜索计划模型调用了几次
- facts 模型调用了几次
- 时间线模型调用了几次
- 每次调用属于哪个服务和操作

远程审计脚本以后会把 trace 一起写进 state。日志也会出现类似：

```text
联网调用统计: 搜索API=1，模型=3（规划=1，facts=1，时间线=1）
```

这样可以直接判断额度花在了哪里，不再根据几十行搜索日志猜测。

## 二、结构化门禁解决“提示词没听话”

提示词是要求，不是强制规则。模型即使收到“不要调换顺序”，仍可能偶尔排错。

因此时间线现在必须提交两类结构化信息：

- 每个节点引用哪些 fact 编号
- facts 抽取阶段给出的本批事件顺序号

程序会在本地检查：

1. fact 编号是否真实存在。
2. 时间线有没有加入引用 facts 中不存在的人物或引语。
3. 同一批资料中的事件顺序是否发生倒退。

例如 facts 的顺序是 `1 -> 2 -> 3`，时间线返回 `1 -> 3 -> 2`，程序会拒绝整条时间线。

如果时间线没有通过校验，系统不会让最终模型自行编排，而会增加限制：只能选择一个有证据的事实自然回答，不得把多个事件串联起来。

这叫“失败收敛”：无法保证远程模型永远正确，但能限制错误继续放大。

## 三、固定回放解决“修 A 坏 B”

固定基线文件是：

```text
test/fixtures/grounding_replay_v1.json
```

它保存了已经接受的第 1 至 9 题的：

- 搜索对象
- facts
- 时间线
- 日语回答
- 中文翻译
- 当时的搜索 API 调用次数

第 1 至 8 题来自已有总报告 state。第 9 题采用此前已经确认正确、包含“水族馆在前，天台归队在后”的报告。

这个 fixture 不会在普通测试时自动更新。当前代码生成了不同结果，也不能偷偷把基线覆盖掉。

## 四、以后如何测试

### 日常改代码

只运行本地测试：

```powershell
flutter test test\grounding_replay_test.dart
```

它不会调用任何远程 API，不消耗豆包或 DeepSeek 额度。

测试会检查：

- 已接受问题是否仍满足最低 facts 数
- 复杂问题是否仍有时间线
- 关键搜索对象有没有丢失
- 已确认的关键事实是否仍存在
- 时间线关键节点有没有排反
- 搜索 API 次数是否超过预算

### 修改正式搜索链路后

先运行：

```powershell
flutter analyze
flutter test
```

两项通过后，才选择一道受影响的问题运行真实 API。该题不合格时立即停止，不继续运行后面的题。

### 接受新的正确结果

只有人工确认新报告确实更好时，才运行：

```powershell
dart run tool\build_grounding_replay_fixture.dart
```

它会明确重建固定 fixture。不要把这个命令放进普通测试或自动构建流程。

## 五、发布门槛

建议发布前满足以下条件：

1. `flutter analyze` 无错误。
2. `flutter test` 全部通过。
3. 固定回放中的所有已接受问题通过。
4. 对本次实际改动影响到的题目逐题运行真实 API，每题通过后才进入下一题。
5. 日志中的搜索 API 调用次数没有超过该题预算。
6. 任何时间线失败都被门禁拦住，没有作为确定剧情进入最终回答。

## 六、仍然不能保证什么

这套改造不能保证任意新问题的模型回答百分之百一致。搜索网页、第三方 API 和语言模型仍然是外部的不确定因素。

它能保证的是：

- 已确认行为有固定基线，不会悄悄回归。
- 可确定检查的错误由代码拦截，不只依赖提示词。
- 普通回归测试不花 API 额度。
- 真实 API 测试的调用次数可以被准确记录。
- 新问题失败时能知道坏在搜索、facts、时间线还是最终表达，而不是继续盲目修改整条链路。
